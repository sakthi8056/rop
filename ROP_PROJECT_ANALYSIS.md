## 1. Executive Summary

This report documents an in-depth, read-only architectural inspection and empirical verification of the **Retinopathy of Prematurity (ROP) AI Screener** software repository (`c:\sakthi_rop`). 

The application is an end-to-end, AI-assisted decision-support platform designed for neonatal intensive care units (NICUs) and rural community health clinics. It facilitates newborn demographic registration, chronological and postmenstrual age tracking, retinal fundus photograph uploading, multi-metric optical quality filtering, 3-tier vascular classification (*Normal*, *Pre-Plus/Mild*, *Plus Disease/Severe*), explainable AI (Grad-CAM) visualization, and print-ready PDF screening report export.

### Key Verified Findings:
1. **Architectural Decoupling**: The system uses a modern client-server architecture. The frontend is built on **React 19** and bundled with **Vite 8**, while the backend is an asynchronous **FastAPI** application backed by **SQLite** via `aiosqlite`.
2. **Dual-Mode AI Engine**: The backend incorporates a dynamic fallback mechanism:
   - **Real Inference Mode**: If trained PyTorch weights exist at `backend/ml/weights/rop_model.pth`, the system runs an **EfficientNet-B0** model and outputs softmax probabilities alongside genuine backpropagation Grad-CAM heatmaps.
   - **Demo Mode**: If model weights are missing or unreadable, the system shifts to a deterministic demonstration mode (`is_demo: true`) with zeroed probabilities, null confidence, and synthetic geometric heatmaps marked "DEMO".
3. **Model Weights Provenance**: The repository currently holds a 16.3 MB weights file (`backend/ml/weights/rop_model.pth`) and companion metadata (`model_metadata.json`). Inspection verifies that this model was trained for 5 epochs on a **synthetic geometric benchmark dataset** (`data/rop_benchmark/`, 25 simulated images/class) generated by `dataset_downloader.py`. It is **NOT** validated on clinical trial data.
4. **Clinical Safety Safeguards**: Clinical decision logic (`services/recommendation.py`) strictly forbids signing off on low-quality or degraded fundus scans as "Screen Negative". Degraded images default to `INCONCLUSIVE / UNGRADABLE – REPEAT IMAGING OR REFER`.
5. **Empirical Test Suite**: Automated verification confirms **21 out of 21 pytest test cases pass** with zero failures. Frontend static linting with Oxlint reveals **0 errors and 17 non-fatal warnings**.

## 2. Project Overview and Objectives

### 2.1 Clinical Purpose
Retinopathy of Prematurity (ROP) is a vasoproliferative vitreoretinal disease affecting premature, low birth weight neonates exposed to supplemental oxygen. Severe, untreated ROP can progress rapidly to retinal detachment and irreversible bilateral blindness. In low- and middle-income countries (LMICs), the acute shortage of certified pediatric ophthalmologists necessitates automated, tele-screening triage solutions.

### 2.2 Software Objectives
- **Demographic & Risk Factor Acquisition**: Capture gestational age (weeks + days), birth weight (grams), postnatal age, and clinical history.
- **Image Quality Verification**: Automatically reject out-of-focus, dark, overexposed, low-resolution, or non-RGB fundus images before AI analysis.
- **3-Class Vascular Classification**: Classify posterior pole retinal fundus photos into:
  1. `Normal` (No abnormal vascular dilation or tortuosity)
  2. `Pre-Plus/Mild` (Abnormal vascular dilation or tortuosity insufficient for Plus)
  3. `Plus Disease/Severe` (Marked vascular dilation and tortuosity in at least 2 quadrants)
- **Visual Attention & Explainability (XAI)**: Render Grad-CAM heatmaps highlighting critical arteriolar and venular arcades.
- **Actionable Referral Urgency**: Map screening outcomes to standardized clinical urgency tiers: *Routine*, *Elevated*, *Urgent*, or *Manual Specialist Review*.
- **Offline Reliability & Reporting**: Function without internet access on rural Windows laptops, providing dual English/Tamil user interfaces and generating vector PDF reports.

## 5. Frontend Architecture

### 5.1 Architecture & Component Hierarchy
The frontend is a Single-Page Application (SPA) designed with a clean, medical-themed CSS architecture (teal, slate, amber, red status tokens). Routing is managed by `react-router-dom` v7.

```
App.jsx (BrowserRouter)
└── AuthProvider (AuthContext)
    ├── Route /login -> LoginPage
    └── ProtectedRoute (Auth Guard)
        ├── Sidebar (Nav items, active indicators, prototype notice)
        ├── Header (Language toggle EN/TA, user profile, logout)
        └── Main Content Outlet
            ├── Route / -> DashboardPage
            ├── Route /register -> PatientRegistrationPage
            ├── Route /screening/:sessionId -> ScreeningPage
            ├── Route /results/:sessionId -> ResultsPage
            ├── Route /history -> HistoryPage
            └── Route /report/:reportId -> ReportPage
```

### 5.2 State Management & Authentication Flow
- **Session Persistence**: JWT access tokens are stored in `localStorage` under `rop_token`.
- **Global Context (`AuthContext.jsx`)**: Manages `user`, `loading`, and `error` states. Upon mount, it executes `GET /api/auth/me` to validate stored tokens.
- **Request Interception (`client.js`)**: Injects `Authorization: Bearer <token>` into outgoing requests. A response interceptor intercepts HTTP 401s, clears credentials, and emits a custom `auth-error` event to immediately redirect users to `/login`.
- **Local Component State**: Pages manage their own lifecycle, async fetching, and validation errors using standard React hooks (`useState`, `useEffect`, `useCallback`, `useMemo`).

### 5.3 User Interface Pages
1. **LoginPage (`pages/LoginPage.jsx`)**:
   - Clean card-based login layout with logo.
   - Dual-language switcher in top-right corner.
   - Pre-configured for default clinician credentials (`admin` / `rop2024`).
2. **DashboardPage (`pages/DashboardPage.jsx`)**:
   - Four top-level metric counters: Total Screenings, Today's Screenings, Pending Reviews, Urgent Referrals.
   - Dynamic banner alerting users if Demo Mode is active.
   - Table of recent 5 screenings with direct navigation to results.
3. **PatientRegistrationPage (`pages/PatientRegistrationPage.jsx`)**:
   - Dual-purpose component: creates new patients or edits existing records via `?edit=<patient_id>`.
   - Real-time preview of auto-generated ID (`ROP-YYYYMMDD-XXXX`).
   - Dynamic clinical calculator (`useMemo`): instantly calculates Chronological Age, Postmenstrual Age (PMA), and Corrected Age in weeks and days as gestational weeks or birth date change.
   - Submits patient data and immediately auto-starts a screening session, redirecting to `ScreeningPage`.
4. **ScreeningPage (`pages/ScreeningPage.jsx`)**:

   - Drag-and-drop fundus photo upload zone via `react-dropzone`.

5. **ResultsPage (`pages/ResultsPage.jsx`)**:

   - High-resolution three-way image toggle: *Uploaded Fundus Scan*, *Grad-CAM Attention Heatmap*, *Vascular Overlay*.

   - Actionable referral recommendation box.

6. **HistoryPage (`pages/HistoryPage.jsx`)**:
   - Full historical registry of all completed, pending, or ungradable screening sessions.

## 6. Backend Architecture and API Endpoints

### 6.1 Application Structure
The backend is structured modularly following FastAPI best practices. The application lifecycle (`lifespan` in `main.py`) performs pre-flight checks: ensures upload and report directories exist, initializes the SQLite database schema, applies migrations, seeds the default administrator, and checks for model weights.

### 6.2 Verified REST API Endpoints

#### Authentication (`/api/auth`)
- `POST /api/auth/register` — Register new user (doctor, nurse, technician). Returns JWT and user payload.
- `POST /api/auth/login` — Authenticate username and password. Returns JWT bearer token.
- `GET /api/auth/me` — Retrieve current authenticated user profile.

#### Patient Management (`/api/patients`)
- `GET /api/patients/next-id` — Previews the next auto-generated patient ID (`ROP-YYYYMMDD-XXXX`).
- `POST /api/patients/` — Registers a new patient. Validates age ranges, birth weight, and phone number.
- `GET /api/patients/` — Lists active patients with pagination (`limit`, `offset`) and search query filtering.
- `GET /api/patients/{patient_id}` — Retrieves detailed patient demographic and clinical record.
- `PUT /api/patients/{patient_id}` — Updates existing patient demographic and contact fields.
- `DELETE /api/patients/{patient_id}` — Soft-deletes patient record (`is_deleted = 1`) and cascades to associated sessions. Requires query parameter `confirm=true`.

#### Screening Sessions (`/api/screening`)
- `POST /api/screening/start` — Initializes a screening session (`SCR-YYYYMMDDHHMMSS-XXXX`) linked to a patient.
- `POST /api/screening/{session_id}/analyze` — Triggers complete screening pipeline: image quality filtering, PyTorch inference (or demo fallback), Grad-CAM generation, and clinical protocol mapping.
- `GET /api/screening/{session_id}/results` — Returns aggregated session findings, images, model output, and clinical status.
- `PUT /api/screening/{session_id}` — Updates screening date and clinical session notes.
- `DELETE /api/screening/{session_id}` — Soft-deletes a session record (`is_deleted = 1`). Requires `confirm=true`.

#### Image Upload & Assessment (`/api/images`)
- `POST /api/images/upload/{session_id}` — Receives multipart/form-data fundus scan (`.jpg`, `.jpeg`, `.png`), checks size (<=10 MB), stores file on disk, runs quality assessment, and records metadata in `screening_images`.
- `DELETE /api/images/{image_id}` — Deletes unanalyzed uploaded image from disk and database.
- `GET /api/images/session/{session_id}` — Retrieves list of uploaded scans and quality scores for a session.

#### History & Audit (`/api/history`)
- `GET /api/history/` — Queries screening history joined with patient demographics, supporting filters for patient ID, name, date range, and status. Excludes soft-deleted records.
- `GET /api/history/{session_id}` — Alias routing to `get_screening_results`.
- `DELETE /api/history/{session_id}` — **Hard-deletes** session, results, images, and reports from SQLite (Note: does not remove files from disk; see Section 16).

#### Clinical Reports (`/api/reports`)
- `POST /api/reports/generate/{session_id}` — Compiles session data, patient ages, scan images, and results into a ReportLab vector PDF. Returns URLs for preview and download.
- `GET /api/reports/download/{report_id}` — Serves binary PDF file as an attachment (`Content-Disposition: attachment`).
- `GET /api/reports/preview/{report_id}` — Serves binary PDF file inline (`Content-Disposition: inline`) for browser display.
- `GET /api/reports/session/{session_id}` — Lists all generated reports for a screening session.

#### System Health & Diagnostics
- `GET /api/health` — Returns application status, version, `demo_mode` flag, and `model_available` flag.
- Static mount `/uploads` — Serves uploaded fundus images and generated Grad-CAM heatmaps.

## 7. AI/ML Architecture and Inference Pipeline

```
Retinal Fundus Image
       │
       ▼
[Image Quality Assessor] ──► (Ungradable? Fail fast -> Require Recapture / Direct Specialist Exam)
       │ (Acceptable / Poor)
       ▼
[Pre-processor] ──► (Lanczos resize to min-dim 224 -> Center Crop 224x224 -> ImageNet norm)
       │
       ├──► [Model Loader] ──► (EfficientNet-B0 + Linear(1280, 3) + Softmax)
       │                             │
       │                             ├──► Class 0: Normal
       │                             ├──► Class 1: Pre-Plus/Mild
       │                             └──► Class 2: Plus Disease/Severe
       │
       └──► [Explainability Engine] ──► (Grad-CAM on model.features[-1] -> Jet Colormap -> Overlay)
```

### 7.1 Neural Network Architecture
- **Base Architecture**: EfficientNet-B0 (`torchvision.models.efficientnet_b0`).
- **Feature Extractor**: 8 sequential inverted residual convolutional blocks (`model.features`), extracting rich spatial and vascular patterns up to 1280 channels.
- **Classifier Head**: Linear projection replacement:
  ```python
  in_features = model.classifier[1].in_features  # 1280
  model.classifier[1] = torch.nn.Linear(in_features, 3)
  ```
- **Inference Classes**:
  - Index 0: `Normal`
  - Index 1: `Pre-Plus/Mild`
  - Index 2: `Plus Disease/Severe`

### 7.2 Preprocessing Pipeline (`backend/ml/preprocessor.py`)
1. **Format Validation**: Converts image to 3-channel RGB.
2. **Aspect-Preserving Resize**: Determines scaling ratio `scale = 224 / min(width, height)`. Resizes using high-quality anti-aliased Lanczos filtering (`Image.LANCZOS`).
3. **Center Crop**: Extracts a square `(224, 224)` patch from the center, preserving retinal geometry without spherical distortion.
4. **Intensity Normalization**: Converts pixel values to float32 range `[0.0, 1.0]`, followed by channel-wise ImageNet standardization:
   - Mean: `[0.485, 0.456, 0.406]`
   - Standard Deviation: `[0.229, 0.224, 0.225]`
5. **Tensor Formatting**: Transposes HWC format to PyTorch standard CHW format `(3, 224, 224)`.

### 7.3 Explainability Module (`backend/services/explainability.py`)
- **Method**: Grad-CAM (Gradient-weighted Class Activation Mapping) via `pytorch_grad_cam`.
- **Target Layer**: `model.features[-1]` (the final convolutional layer before global pooling).
- **Target Class**: Evaluated with respect to the highest-scoring predicted class (`ClassifierOutputTarget(predicted_class)`).
- **Visualization Artifacts**:
  1. Grayscale activation map normalized `[0, 1]`.
  2. Pseudo-color thermal map using OpenCV's `COLORMAP_JET`.
  3. Alpha-blended composite overlay (`0.6 * original + 0.4 * heatmap`), saved as a PNG in `backend/uploads/`.

### 7.4 Image Quality Assessment (`backend/services/image_quality.py`)
Before inference, every image undergoes multi-metric validation:
1. **Resolution Check**: Minimum 200×200 pixels required.
2. **Color Check**: Must have 3 channels (RGB).
3. **Sharpness / Blur Variance**: Computes the variance of the 64-bit Laplacian operator:
   $$\sigma^2 = \text{Var}(\nabla^2 I)$$
   Threshold set to $\sigma^2 \ge 100.0$.
4. **Illumination & Brightness**: Mean grayscale luminance must fall within `[40.0, 220.0]`.
5. **Contrast Standard Deviation**: Minimum standard deviation of 20.0 required.
6. **Aspect Ratio Limit**: Extreme aspect ratios exceeding 3.0:1 are rejected.
7. **Artifact / Desaturation Check**: Evaluates HSV saturation channel (mean > 10).

Images failing critical checks are labeled `UNGRADABLE`. Images with minor degradation are scored `POOR`.

### 7.5 Model Weights Provenance & Training Status
- **Current Checkpoint**: `backend/ml/weights/rop_model.pth` (16,339,659 bytes).
- **Companion Metadata (`model_metadata.json`)**:
  - Architecture: `EfficientNet-B0`
  - Training Epochs: 5
  - Best Validation Accuracy: 1.0 (100.0%)
  - Timestamp: `2026-09-19T18:36:49 UTC`
- **Data Ground Truth**: Inspection of `data/rop_benchmark` reveals that this model was trained on 75 synthetic images generated by `dataset_downloader.py` (red circular disks with synthetic lines simulating vessels). 
- **CRITICAL DISTINCTION**: The current weights represent an **algorithmic pipeline proof-of-concept**. They **DO NOT possess clinical diagnostic validity**. The software authors explicitly acknowledge this in `TRAINING_GUIDE.md` and reference legitimate public datasets (FARFUM-RoP, Macretina, Kaggle, ROP-VL) for real clinical training.

## 12. Offline Functionality

The software is exceptionally well-suited for disconnected, rural field clinic deployment:
- **Zero Cloud API Dependencies**: The application makes no external API requests to OpenAI, Google Cloud, AWS, or third-party inference endpoints.
- **Local Database**: SQLite 3 runs embedded inside the Python runtime, with zero database server setup.
- **Self-Contained ML Runtime**: PyTorch weights are loaded directly from local disk (`backend/ml/weights/rop_model.pth`).
- **Local PDF Engine**: ReportLab builds vector PDFs in pure Python without requiring remote rendering engines or external font servers.
- **Defect / Limitation**: The frontend API URL is hardcoded in `frontend/src/api/client.js` as `http://localhost:8000/api`. If healthcare workers attempt to access the frontend from a tablet over a local clinic Wi-Fi network, the tablet browser will fail to reach the backend unless configured to use the host machine's LAN IP address.

## 16. Bugs, Errors, and Limitations

### 16.1 High Severity Issues

#### 1. Synthetic Training Data in Model Weights Checkpoint
- **Affected File**: `backend/ml/weights/rop_model.pth`, `backend/ml/weights/model_metadata.json`
- **Evidence**: `model_metadata.json` records 100% validation accuracy across 5 epochs. Inspection of `data/rop_benchmark` confirms the training source was 75 procedurally drawn circles with simulated lines.
- **Impact**: While the model loads and executes real PyTorch inference without errors, **its classifications on real human infant fundus photographs are medically meaningless**.
- **Recommended Action**: Retrain the model on open-access clinical collections (FARFUM-RoP, Macretina) or place the system back into Demo Mode until clinical weights are supplied.

#### 2. Deletion Inconsistency (Soft Delete vs Hard Delete Orphan Risk)
- **Affected Files**: `backend/routers/screening.py:418`, `backend/routers/history.py:129-133`
- **Evidence**: `DELETE /api/screening/{session_id}` marks records as soft-deleted (`is_deleted = 1`). In contrast, `DELETE /api/history/{session_id}` executes SQL `DELETE FROM screening_results`, `DELETE FROM screening_images`, `DELETE FROM reports`, `DELETE FROM screening_sessions`. Crucially, it **does not delete image files or PDF reports from the filesystem**.
- **Impact**: File storage in `backend/uploads/` and `backend/reports/` leaks orphaned data indefinitely, presenting privacy compliance violations.
- **Recommended Action**: Standardize all deletions on soft deletion or ensure file unlink operations (`os.remove`) accompany database row deletion.

#### 3. Hardcoded Development JWT Secret
- **Affected File**: `backend/config.py:50`
- **Evidence**: `JWT_SECRET_KEY: str = "rop-screening-local-dev-secret-change-in-production"`
- **Impact**: Any attacker with read access to the source code can forge arbitrary JWT bearer tokens and impersonate administrators or clinicians.
- **Recommended Action**: Enforce loading `JWT_SECRET_KEY` from an environment variable with a strong cryptographic random default.

## 17. Security, Privacy, and Clinical Safety

### 17.1 Security & Authentication Posture
- **Password Protection**: Passwords are securely hashed using `bcrypt` with automated salting. Passwords longer than 72 bytes are safely truncated to avoid bcrypt buffer exceptions.
- **JWT Authorization**: API routes are protected using FastAPI's `HTTPBearer` dependency. Tokens expire after 8 hours (`JWT_EXPIRATION_MINUTES = 480`).
- **CORS Configuration**: Restricts origins to `http://localhost:5173` and `http://127.0.0.1:5173`.
- **SQL Injection Prevention**: All SQL statements use parameterized queries (`?` syntax in `aiosqlite`), preventing SQL injection attacks.

### 17.2 Patient Privacy (PHI) Risks
- **Unencrypted Database**: Patient identifiers, dates of birth, and parent contact details are stored in plain text in `rop_screening.db`.
- **Unprotected Image Storage**: Retinal scans in `backend/uploads/` are stored unencrypted on the filesystem. The `/uploads` static route serves images to any client with the filename without requiring a JWT token.
- **Recommendation**: Implement authenticated streaming for `/uploads/` and encrypt SQLite databases at rest (e.g., using SQLCipher).

### 17.3 Clinical Decision Safety Safeguards
The codebase incorporates several critical clinical decision safety invariants:
1. **No False Negatives on Degraded Images**: In `services/recommendation.py`, if an image is scored `POOR` and the AI predicts `Normal` (or confidence is $<0.65$), the system **refuses to report Screen Negative**. It automatically overrides the status to `INCONCLUSIVE / UNGRADABLE – REPEAT IMAGING OR REFER`.
2. **Transparent Demo Mode**: When real model weights are absent, confidence is set to `null` and probabilities to `0.00%`. The UI and PDF reports display high-visibility orange warning banners.
3. **No Direct Drug / Treatment Prescriptions**: The recommendation engine restricts outputs to screening intervals (e.g., "1–2 week follow-up", "Immediate specialist referral") and never prescribes laser photocoagulation, anti-VEGF injections, or medications.
4. **Statutory Research Disclaimers**: Prominently presented on every dashboard, screening result screen, and exported PDF.

## 18. Missing or Partially Implemented Features

1. **Clinician Confirmation / Sign-Off Workflow**:
   - The current UI displays AI predictions and recommendations, but lacks a formal sign-off interface where an attending ophthalmologist can record a confirmed diagnosis, BIO examination notes, and digital signature.
2. **Multi-Image / Bilateral Eye Session Aggregation**:
   - Although multiple scans can be uploaded per session, the current inference router processes images independently and presents the primary result of the first image on the summary banner, rather than computing a patient-level bilateral staging diagnosis (Worst Eye staging).
3. **Zone and Stage Detection**:
   - The AI classifier is restricted to vascularPlus disease classification (*Normal*, *Pre-Plus*, *Plus*). It does not detect ROP Zones (Zone I, II, III), peripheral stages (Stage 1 demarcation line through Stage 5 total detachment), or aggressive ROP (A-ROP).
4. **Role-Based Access Control (RBAC) Enforcement**:
   - While the `users` table contains roles (`doctor`, `nurse`, `technician`), all authenticated users have identical permissions across all endpoints.

## 19. Recommendations for Future Improvements

### Technical Architecture
1. **Dynamic Environment Configuration**: Migrate frontend `api/client.js` to `import.meta.env.VITE_API_URL` to enable deployment on local area networks and portable tablets.
2. **Secure Media Serving**: Remove public static mounts for `/uploads` and `/reports`. Serve images and PDFs through authenticated endpoints checking JWT permissions.
3. **Storage Cleanup Hooks**: Attach disk deletion hooks to `DELETE /api/history/{session_id}` and `DELETE /api/screening/{session_id}` to clean up orphaned image and PDF files.

### Clinical & AI Enhancements
1. **Clinical Weights Retraining**: Train the EfficientNet-B0 backbone on verified clinical datasets (such as FARFUM-RoP or Macretina) using the existing `backend/ml/train.py` pipeline.
2. **Tamil Font Integration**: Bundle `NotoSansTamil-Regular.ttf` in `backend/static/fonts/`, register it with ReportLab, and connect the frontend language selector to PDF report generation.
3. **Clinician Audit Log**: Introduce an `audit_logs` table tracking every screening review, patient edit, and report download with timestamp and user ID.
4. **Bilateral Worst-Eye Staging**: Aggregate right eye (`OD`) and left eye (`OS`) assessments to compute an overall patient triage status.
